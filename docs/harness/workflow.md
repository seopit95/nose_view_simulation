# 개발 절차와 범위 이탈 방지

목표는 버그를 줄이고 재현·검증·복구할 수 있게 만드는 것이다. “꼼꼼하게”라는 지시만 반복하지 않고, 한 작업마다 입력·변경·검증·근거를 남긴다.

## 1. 시작: 목표를 고정한다

1. 실제 작업 루트를 확인하고 [status.md](status.md)를 읽는다. Git 사용 여부와 기존 변경을 확인한다. 저장소가 없으면 Git 명령 성공을 전제하지 않는다.
2. 현재 요청을 한 문장으로 요약하고, 사용자에게 짧은 작업 계획을 알린다.
3. 관련 지침·구현·호출부·테스트를 읽는다. 기억이나 오래된 ZIP을 현재 소스로 사용하지 않는다.
4. 목표, 허용 변경 범위, 제외 범위, 관찰 가능한 완료 조건, 실행할 검증을 고정한다.
5. 여러 파일/여러 단계 작업과 버그 수정은 [task-template.md](task-template.md)로 작업 기록을 만든다. 단순 오탈자·문서 링크 수정은 새 계획 파일 없이 변경과 검증만 기록해도 된다.

작업 문서는 필요할 때 `docs/harness/tasks/YYYY-MM-DD-topic.md`로 생성한다. 상태는 파일 내부의 `active / blocked / completed`로 관리하고 [status.md](status.md)에서 현재 작업을 링크한다. 빈 계획 파일을 미리 쌓지 않는다.

## 2. 설계: 현재 구조 안에서 가장 작은 해법을 선택한다

- 현재 요청을 해결하는 기존 함수·컴포넌트·브라우저 기능·설치된 라이브러리를 먼저 찾는다.
- 바뀌는 계약과 실패 경로를 적는다. 새 경계를 만들면 입력·출력·오류·취소·자원 소유자를 정의한다.
- 카메라·Worker·렌더링을 건드리면 [architecture.md](architecture.md)의 해당 INV 번호를 연결한다.
- 변경 이유를 목표에 연결할 수 없는 파일은 수정하지 않는다. 필요한 보조 변경이 발견되면 이유를 작업 기록에 추가한다.
- 전면 리팩터링, 스택 교체, 새 백엔드, 새 의존성, 새 환자 데이터 흐름으로 커지면 현재 목표로 해결 가능한지 다시 판단한다. 별도 제품 선택이 필요하면 구현 전에 사용자에게 확인한다.
- 새 코드의 편의를 위해 개인정보·오프라인·프레임 정합성 계약을 완화하지 않는다.

## 3. 버그: 재현하고 원인을 좁힌다

1. 기대 동작 / 실제 동작 / 재현 단계 / 실행 환경 / 입력 종류를 기록한다.
2. 원본 오류를 짧은 재현이나 테스트로 먼저 확인한다. 가상 장치와 실물 장치를 구분한다.
3. 관련 호출부와 상태·자원 경로를 추적해 가설 하나를 세운다. 증상별 임시 guard를 여러 곳에 붙이지 않는다.
4. 원인을 잡는 회귀 검증을 추가하거나 기존 검증을 보강한다. 실제로 잘못된 동작을 검출하는지 확인한다.
5. 최소 수정 후 재현 검증 → 인접 영향 검증 순서로 수행한다.
6. 재현 불가면 장치·시간·상태 순서 등 부족한 관측을 기록한다. 고쳤다고 보고하지 않는다.

증거 없는 수정을 두 번 했는데도 같은 문제가 남으면 코드를 더 덧붙이지 않는다. 기존 가설과 결과를 정리하고 입력·경계·환경을 다시 조사한다. 이는 원인 재검토 지점이며 자동으로 작업을 포기하거나 전체 앱을 재작성하는 근거가 아니다.

## 4. 구현: 한 번에 하나의 이유로 바꾼다

- 기능·버그는 관찰 가능한 인수 조건을 먼저 정하고 필요한 검증을 만든다. 테스트는 구현을 베끼는 대신 실패하면 사용자에게 영향이 생기는 계약을 검사한다.
- TypeScript strict를 유지한다. 경계 입력을 보정·검증하고, 의미 없는 `any`, `@ts-ignore`, 비어 있는 catch로 오류를 감추지 않는다.
- UI 텍스트·접근성을 유지하며 이벤트 식별은 role/label/텍스트를 우선한다. 좌표 클릭과 고정 sleep은 피한다.
- 프레임/비동기 작업에는 취소·stale 결과·실패·자원 정리 경로를 함께 다룬다.
- 요청 범위 밖 장애를 발견하면 영향과 재현 근거를 현황에 남긴다. 현재 완료 조건을 막으면 선행 해결로 포함하되 이유를 명시한다.
- 사용자 변경을 덮어쓰지 않는다. 파일 삭제·강제 초기화·캐시 일괄 삭제·로그인·인증서 작업은 사전 확인 규칙을 따른다.
- 에이전트 여러 개의 실행을 기본 전제로 삼지 않는다. 위임을 별도로 허용받은 경우에만 파일 소유 범위와 합칠 검증을 명시한다.

## 5. 검증: 실패를 피드백으로 사용한다

- [quality.md](quality.md)의 변경 유형별 검증을 실행한다. 의존 관계가 있는 빌드→실행 검사는 순서대로 수행한다.
- 테스트 실패 시 원래부터 있던 실패인지 구분하되, 필요한 검증이 실패한 상태를 완료로 표시하지 않는다.
- 테스트를 삭제/skip하거나 허용 오차·timeout을 근거 없이 늘려서 통과시키지 않는다. 비결정적 실패는 재현 순서와 환경을 보존한다.
- Vitest 수집은 `vitest.config.ts`의 `tests/**/*.test.{ts,mjs}`로 제한한다. 백업·과거 소스의 시험이 섞여 통과 수가 늘지 않았는지 확인한다.
- 빌드 전 검사는 아직 생성되지 않은 out/outputs/qa를 필수 입력으로 요구하지 않는다. 소유 문서의 깨진 링크는 실패로 처리하고, 앱·배포 생성물은 빌드 후 경로/해시 검사로 확인한다. QA와 백업은 버전 관리에서 제외한다.
- 코드 리뷰는 요구사항 누락 → 상태/자원 → 데이터/권한 경계 → 회귀 → 불필요한 변경 순으로 한다. 리뷰에서 발견한 문제는 검증 가능한 작업으로 되돌린다.
- 전체 검증을 한 번 통과했다면 새 변경·실패·미해결 의문 없이 반복 실행하지 않는다.
- 원격 CI는 아직 없다. `npm run verify`는 문서/단위 검사 → 새 패키징 → 대상 해시 검증 → 통합/상태 경합/권한 검사 → audit를 순서대로 실행하고 첫 실패에서 멈춘다.
- 검증 중 소스를 편집하거나 같은 폴더에서 Electron 검사 두 개를 동시에 실행하지 않는다. 먼저 하나를 끝내고 결과를 확인한다.

## 6. 종료와 다음 세션

완료 조건 전부를 대조한다. 변경 파일, 실행한 명령과 종료 결과, 검증 환경, 남은 제한을 작업 기록에 남긴다. 필수 실물 테스트를 못 했으면 코드 작업 완료와 실물 검증 미완료를 분리한다.

긴 작업의 중간 지점에는 다음을 저장한다. 다음 세션은 이 기록과 실제 파일 상태를 대조한 후 재개한다.

- 목표와 사용자 승인/변경 범위.
- 바꾼 파일과 현재 단계, 완료·실패·미실행 검증.
- 확인된 원인/결정, 버린 가설과 그 근거.
- 바로 다음 한 단계와 필요한 입력·장치.
- 현재 빌드·보고서 위치. 실제 얼굴·프레임·토큰·비밀번호는 기록하지 않는다.

사용자에게 결과, 검증, 제한을 짧게 보고한다. 테스트 수만으로 수술 결과의 정확도나 상용 준비 상태를 주장하지 않는다.

## 문서가 낡지 않게 유지한다

- 제품 범위는 product, 경계/상수는 architecture, 검증 절차는 quality, 데이터/배포는 privacy-release, 선택 이유는 decisions, 현재 사실은 status가 소유한다.
- 상태 문서에 전체 과거 로그를 누적하지 않는다. 상세 근거는 작업 문서에 두고 현재 상황과 링크만 남긴다.
- 명령·경로·동작을 바꾼 작업에서 관련 링크와 설명도 바꾼다. 과거 검증 보고서는 날짜와 대상을 유지한다.
- 같은 실수가 재발하면 회귀 테스트나 한 가지 구체적 규칙으로 고정한다. `AGENTS.md`에 장문 사건 기록을 계속 추가하지 않는다.
- 검증 코드 자체가 잘못되면 앱의 실패로 단정하지 않는다. 실제 증상인지, fake timer·fixture·수집 범위 문제인지 확인한 후 원래 결함을 검출하는 실패를 다시 얻는다.
- 문서가 구현과 다르면 실제 동작을 기록하고 의도된 계약 위반인지 판단한다. 코드가 있다고 잘못된 동작을 정당화하거나, 문서만으로 구현됐다고 주장하지 않는다.
