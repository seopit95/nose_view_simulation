# 품질 기준과 검증 절차

이 문서는 **무엇을 실행하고 어떤 근거로 통과를 판단할지** 관리한다. 결과는 [status.md](status.md)와 개별 작업 기록에 남긴다. 버그 0개를 보증하는 대신 실패를 재현하고 회귀를 막는다.

## 실행 환경과 명령

명령은 현재 NoseView 프로젝트 루트에서 실행한다. Node 요구사항과 스크립트 이름의 기준은 [package.json](../../package.json), 설치 버전의 기준은 [package-lock.json](../../package-lock.json)이다.

```sh
node --version
npm --version
```

Node는 현재 `>=22.12.0`이다. 의존성이 없거나 잠금 파일이 바뀐 새 개발 환경이면 `npm ci`가 설치 재현 명령이다. 이 명령은 기존 `node_modules`를 제거·재설치하므로 삭제 사전 확인 규칙이 적용되는 환경에서는 실행 전에 확인한다. 정상 설치를 이유 없이 다시 설치하지 않는다. 검증 통과를 위해 잠금 파일을 임의 재생성하지 않는다.

| 명령 | 하는 일 / 선행조건 |
|---|---|
| `npm test` | Vitest 단위·회귀·패키지 검사기·문서 연결 시험. `tests` 안의 시험만 수집하며 얼굴 모델 자체는 실행하지 않는다. |
| `npm run typecheck` | TypeScript strict 검사. 실행 오류·시각 품질·CJS 런타임까지 보증하지 않는다. |
| `npm run build` | 로컬 모델 SHA-256 확인, WASM 복사, 타입 검사, Worker/renderer 빌드. dist 생성물 갱신. |
| `npm run dev` | 브라우저 개발 서버. Worker 변경 후 재시작. Electron 저장·권한 검증을 대체하지 않는다. |
| `npm start` | 새 빌드 후 개발용 Electron 실행. 카메라는 연결 동작 전까지 열지 않는다. |
| `npm run test:e2e` | **선행: build.** 개발 Electron의 기본 통합 → 화면/상태 → 촬영 보정 → 기본 설정 → 여러 코 타입 → 실시간 필터 → 측면/부위 → 간편 상담 UX → UI 배치 검사를 순차 실행. |
| `npm run package` | 새 빌드와 현재 OS/아키텍처 앱 생성. ZIP은 만들지 않는다. |
| `npm run make` | 새 빌드와 현재 OS/아키텍처 앱·ZIP 생성. |
| `node scripts/run-packaged-test.mjs` | **선행: 현재 폴더에서 package 또는 make.** 대상 경로·소스/앱 해시 검사 후 예시 제외 → 카메라 시작 실패/재시도 → 측면 GPU → 실제 모델 부위 → 기본 E2E → 상태 경합 → 촬영 보정 → 기본 설정 → 여러 코 타입 → 실시간 필터 → 간편 상담 UX → UI 배치 → 가상 권한 검사를 순서대로 실행. |
| `node tests/camera-permission.mjs` | **선행: 새 패키지.** 독립 실행 시에도 동일한 대상 검증 후 가상 장치로 권한 handler·마이크 거부·트랙 종료 확인. qa 폴더 자동 준비. |
| `npm run verify` | 단위/문서 → make(타입/빌드 포함) → 패키지 전체 통합/권한 → audit. 실패 시 다음 단계 실행 안 함. |
| `npm audit` | 해당 시점의 의존성 취약점 조회. 네트워크 실패는 “0개”가 아니다. |

`npm run lint`, `npm run test:camera`, CI 워크플로는 현재 존재하지 않는다. 없는 명령이 검증됐다고 쓰지 않는다. `tests/smoke.mjs`는 보조 화면 검사이며 실제 통합 시험을 대체하지 않는다.

여러 타입의 저장/선택 회귀는 [nose-presets.test.ts](../../tests/nose-presets.test.ts)와 [nose-presets.mjs](../../tests/nose-presets.mjs)가 담당한다. v1/v2 원본 유지 이전, v3 이름·ID·기본 대상·상한과 코8필드 검증, 여러 타입 추가/취소/이름 변경/중복/저장 실패/재실행/새 상담/필터 첫 연결/최소 창과 실제 GPU 변화를 확인한다. 저장소 오류는 경계 주입, 카메라는 합성 captureStream이며 실물 검증을 뜻하지 않는다. 새 저장 구조를 바꿀 때 읽기만으로 이전 저장값을 덮어쓰지 않는 회귀를 유지한다.

## 변경 유형별 최소 검증

| 변경 | 필수 검증 |
|---|---|
| Markdown만 | `npm test -- tests/harness.test.mjs` + 명령·소스 설명·현재/과거 상태 대조. 앱 재빌드 불필요. 배포에 포함되는 THIRD_PARTY_NOTICES.md는 예외. |
| 스타일/문구/레이블 | build + 해당 화면/키보드/창 크기 확인. 연결된 E2E 선택자가 있으면 함께 확인. |
| geometry / frame-gate / pipeline | 관련 회귀 시험 → `npm test` → build → Electron E2E. |
| App 카메라·상담 상태 / Worker / Viewport | 관련 회귀 시험 → `npm test` → build → Electron E2E. 변경한 장애 경로를 추가 확인. |
| PNG / preload / main / CSP / 권한 | `npm run verify` + 변경한 경계 사례 확인. |
| 모델 / WASM / Electron / 의존성 / 빌드 스크립트 | `npm run verify` + 모델/라이선스 변화 확인. |
| 전달할 앱/ZIP 생성 | `npm run verify` → ZIP 내용·무결성·대상 해시. OS별로 각각 수행. |
| 카메라 호환/성능/상품화 주장 | 해당 자동 시험 + 아래 실물/장시간 시험. 자동 시험 통과만으로 완료 처리 금지. |

한 build가 typecheck를 포함하므로 동일 소스에 둘을 계속 중복 실행할 필요는 없다. 패키지 E2E도 동일한 E2E 코드를 실행하므로 같은 변경에서 소스 E2E까지 불필요하게 반복할 필요는 없다. 다만 단위 시험을 패키지 시험으로 대체하지 않는다.

## 개발 코드의 일반 검증 순서

```sh
npm test
npm run build
npm run test:e2e
```

각 명령의 종료 코드와 출력을 확인하고 다음으로 진행한다. 여러 명령을 연결해 마지막 명령 성공으로 앞선 실패를 숨기지 않는다. E2E는 Electron 창과 `qa/` 결과를 생성하므로 동일 폴더에서 동시에 여러 번 실행하지 않는다.

## 복사된 폴더에서 패키지 검증하기

`out/latest-build.json`에는 **절대 경로와 소스/앱 해시**가 들어 있다. 복사 전 폴더·오래된 metadata·변경된 소스/앱·서로 다른 앱의 실행 파일과 archive 조합은 검증기가 실행 전에 거부한다. 파일이 존재한다는 사실만으로 현재 소스의 패키지라고 판단하지 않는다.

```sh
npm run verify
```

개별 명령으로 실행할 때는 `npm test` → `npm run make` → `node scripts/run-packaged-test.mjs` → `npm audit` 순서다. 패키지 검사는 가상 권한까지 포함하므로 다시 중복 실행하지 않는다. `package`는 metadata에 ZIP 경로를 적어도 ZIP 파일을 생성하지 않으므로 ZIP 검증에는 `make`를 사용한다.

[build-info.mjs](../../scripts/build-info.mjs)가 실제 경로와 소스·archive 해시, 실행 파일/archive가 같은 패키지인지 검사한다. `NOSEVIEW_EXECUTABLE`을 직접 지정해 개별 E2E를 실행하면 이 검증을 우회할 수 있으므로 공식 완료 판정에는 검증 wrapper를 사용한다. 검증 도중 소스나 패키지를 편집하지 않는다.

E2E는 `tests/fixtures/`의 합성 이미지를 `canvas.captureStream()` 영상으로 주입한다. fixture를 제품 경로/숨은 예시 기능으로 재도입하지 않는다. 모든 Electron 시험에 `--use-fake-device-for-media-stream`을 넣어 hook 전 자동 연결 회귀도 물리 웹캠에 접근하지 않게 한다. `--use-fake-ui-for-media-stream`으로 권한을 자동 허용하면 handler 검증이 달라지므로 추가하지 않는다. 실제 모델을 검증한다고 표시한 E2E에서는 모델 결과를 대체하지 않는다. 별도 `profile-filter.mjs`의 알려진 좌표 시험은 보고서에도 종류를 명시한다. 2D 사진 회전은 roll 검사이며 좌우 yaw/실제90° 검출 시험으로 계산하지 않는다.

## 변경 시 선택할 장애·경계 시험

0.3부터 모든 공식 Electron 검사는 [electron-launch.mjs](../../tests/electron-launch.mjs)의 독립 user-data-dir를 사용한다. 사용자의 저장 기본값을 읽거나 덮어쓰지 않는다. 기본 설정 검사는 같은 독립 프로필로 실제 종료/재실행해 영속성을 검증한다. 별도 재실행 없는 reload만으로 이를 대체하지 않는다.

전역 톤이 얼굴 없음/각도 불량에서도 유지되는지 실제 픽셀로 확인한다. 피부 질감은 회전 합성 얼굴의 실제 모델 좌표로 검사하고 코 변형·PNG 차단을 함께 확인한다. 그림자/하이라이트 조합의 256단계 회색 순서와 음수 밝기+비정수 대비에서 검정/흰색 끝점을 검사한다. 슬라이더의 단독 끝값만으로 조합의 NaN·밝기 역전을 놓치지 않는다. 작은 창의 저장 버튼뿐 아니라 설정창에서 키보드로 선택한 슬라이더가 고정 하단 버튼 뒤에 가리지 않는지 확인한다.

코 부위 효과를 바꿀 때는 단독±100뿐 아니라 서로 다른 부호의 조합, 짧은 코·입술 간격, 부위가 한 점으로 뭉친 입력도 검사한다. 경계 감쇠를 좁히면 합성 변위의 기울기가 역전될 수 있으므로 유한 차분 Jacobian의 표본 기준>.05를 유지한다. 정면/90°만으로 중간 각도의 끊김을 놓치지 않도록 연속 yaw 표본과36/42° GPU 회귀를 유지한다. 숨은 쪽 투영의 순서 변화와 보이는 쪽 좌표의 붕괴를 구분한다. CPU/GPU 상수·합성 순서·보호 마스크를 함께 검토하고, 세부 무효화/현재 프레임 복구와 PNG 안내8값 잘림도 확인한다.

부위의 이름/설명을 바꿀 때 저장 key만 확인하지 않는다. 해당 축의 단독 효과와 함께 움직이면 안 되는 축/주변 경계를 CPU와 실제 GPU에서 확인한다. 콧구멍 노출량·수술법·코끝 회전처럼 구현하지 않은 의미를 표시명에 붙이지 않는다. 상담/설정/필터/PNG는 같은 메타데이터를 사용한다.

접기 UI는 기본 노출 개수, 키보드 펼침/닫기, 값과 영상 유지, 숨은 적용값 표시를 검사한다. 최소 창의 OS 타이틀바를 제외한 실제 innerHeight로 문서 넘침을 검사하고 내부 패널 스크롤 및 저장 버튼 접근을 유지한다. 설정창의 위쪽/고정 하단 초점 여백을 모두 확인하고, 최소 창에서 필터 설정 목록을 펼쳐도 다시 재생 버튼이 미리보기 바깥에 잘리지 않아야 한다.

UI 스타일 변경은 CSS 수치를 그대로 베끼는 시험 대신 실제 창 크기와 조작으로 확인한다. 선택된 버튼은 hover 상태의 글자 대비도 검사하고, overflow로 잘리는 자식 버튼은 키보드 초점 윤곽이 실제로 보이는지 캡처로 확인한다. OS 모션 줄이기에서 animation/transition이 꺼지는지, 다이얼로그 저장/동의/취소가 화면 안에 들어오는지 확인한다. 실제 모델의 특정 자세 프레임을 정지시켜 비교하는 시험은 자세 확인과 정지를 같은 UI 실행 구간에서 수행한다. 별도 클릭의 안정화 대기 중 다음 프레임으로 바뀔 수 있으며, 과거 메시지를 정지 프레임의 품질로 간주하면 안 된다. 모델 결과를 바꾸거나 픽셀 성공까지 반복하는 방식으로 이를 숨기지 않는다.

필터와 상담 품질을 분리할 때는 같은 정지 프레임에서 모드를 바꾸어 픽셀을 검사한다. 필터가 회전 얼굴에 적용돼도 상담 저장 조건은 엄격하게 유지돼야 한다. 탭 이동의 연결 횟수·캔버스 동일성·정지 의도를 함께 확인하고, 필터 안의 장치 변경·연결 실패/취소·늦은 stream·mute·해제·fatal에서 고정 수치의 유지/초기화를 명시적으로 검사한다.

아래 목록은 필요한 검증 목록이다. 전 항목이 이미 자동화됐다는 뜻이 아니다.

- 카메라: 연결 직후 취소, 빠른 입력 변경, 늦은 성공/실패, 권한 거부, 장치 없음/점유, play 실패, mute/unmute/ended, 반복 연결.
- 프레임: 응답 지연/중복/이전 세대, bitmap 취득 실패, 처리 중 정지/종료, Worker 시작·추론 오류·시간 초과, 미해제 bitmap/Worker.
- 얼굴: 없음/둘 이상, 작음/잘림/행렬 누락/비유한 좌표, 자세 경계의 양쪽, 모델 출력 이상, 손·머리카락·안경·마스크 가림.
- 렌더링: 0·양/음 최대 조절, 코 영역 밖 보존, 거울·회전·비교 경계, 다른 종횡비, 정지 후 조절, WebGL 초기화·context 상실.
- 입력 전환은 정사각형 합성 입력만으로 검증하지 않는다. 최소16:9·4:3·세로 입력, 연결 중 해상도 변경·다른 카메라 입력 복귀를 포함하고 실제 렌더 픽셀을 현재 입력과 비교한다. 추적 성공 메시지만으로 영상 정합성을 통과시키지 않는다. 같은 크기에서 내용이 바뀌는 후속 프레임도 확인한다.
- 촬영 보정은 고해상도 입력에서 같은 보정의 원본/가상 0변형과 PNG 양쪽을 비교한다. 비보정 입력과 직접 비교할 때는 보정 없음을 선택한다. 피부 강도만 변경해 코·눈·눈썹·입술의 픽셀 보존을 검사하고, 밝기/색온도 전체 적용을 흐림 보호 실패로 판정하지 않는다. 얼굴 비율·회전 변화의 보호 영역은 단위 시험도 병행한다.
- “보정 범위 확대”는 슬라이더 max 값만 검사하지 않는다. 동일 프레임의 별도 지정 피부 영역에서 효과가 적용되는 픽셀 비율과 강도 40/100의 같은 영역 질감을 확인하고 밝기 ±30→±100, 색온도 ±50→±100의 실제 영상 차이를 검사한다. 검사 영역을 앱의 마스크 함수로 생성해 자기 구현만 확인하지 않는다.
- 추론용 임시 canvas를 추가하면 성공뿐 아니라 추론 예외 뒤 픽셀 해제를 검증한다. 캔버스 재사용이 이전 촬영 픽셀 보존으로 이어지지 않게 한다.
- 상담: 입력 전환·새 상담·앱 종료 뒤 이전 영상/설정/저장 미리보기 노출 없음, 숨김→복귀 중 트랙 이벤트 경합.
- 저장: 동의 전 차단, 동의 초기화, 취소, 쓰기 실패, 중복 클릭, 기존 파일 보존, 잘못된 sender/frame·PNG signature·크기·동시 요청 거부.
- 앱: 오프라인 콜드 로드, 외부 fetch/navigation/window 차단, 손상/누락된 로컬 모델, GPU 실패→CPU, 둘 다 실패 시 오류 유지.

시험 결과에는 실행한 사례만 체크한다. 픽셀 판정의 허용 오차를 바꾸려면 색공간·OS·GPU 차이 근거와 새 기준을 먼저 기록한다.

## 실물 웹캠 시험

일반 USB 웹캠을 실제로 연결할 수 있는 환경에서 다음 표를 복사해 작업 기록에 채운다. 촬영 대상의 동의와 데이터 사용 범위가 정해지지 않았다면 실제 얼굴 촬영·저장을 시작하지 않는다. 자동 테스트의 합성 예시를 우선 사용한다.

| 구분 | 기록 / 관찰 |
|---|---|
| 환경 | 날짜·앱 버전/해시·OS 버전·CPU/GPU·RAM·웹캠 모델·USB 허브 유무·실제 선택 해상도/fps·delegate |
| 시작/권한 | 앱 시작 때 카메라 꺼짐, 정상 OS 권한 허용/거부 후 상태와 안내, 다른 앱 점유 |
| 연결 | 연결/해제 20회, 처리 중 USB 분리·재연결 10회, 입력 장치 변경. 반복 수와 실패 횟수 기록 |
| 상담 | 조절·A/B/C·원본/비교·거울·일시정지·새 상담. 이전 프레임·설정이 남는지 확인 |
| 환경 변화 | 정상/낮은/역광 조명, 다양한 얼굴·거리·각도·가림, 화면 밖 이동, 빠른 움직임, 두 사람 |
| 촬영 보정 | 보정 없음/자연스럽게/소프트/화사하게 및 슬라이더의 끝값. 피부 질감·눈/입/코 선명도·피부톤/색감·보정 경계 깜빡임을 비교하고 상담용 기본값에 대한 사용자 선호 확인 |
| OS 변화 | 앱 숨김/복귀, 잠자기/깨우기, 해상도/창 크기 변화 후 상태·재연결 가능 여부 |

| 연속 실행 | 초기 점검 30분, 외부 파일럿 전 8시간. 중간 상태와 마지막 재연결·새 상담 확인 |

반복 횟수와 시간은 **앞으로 적용할 프로젝트 점검 기준**이다. 이미 통과한 횟수나 의료 성능 기준으로 인용하지 않는다. 실패 시 재현 시간·직전 동작·자원 사용량을 남기고 수정 후 관련 구간부터 다시 확인한다.

## 성능과 자원 관측

- 동일 장치·해상도·조명·입력·설정에서 변경 전후를 비교한다. 1분 준비 후 5분씩 3회 측정하고 표본 수와 측정 방법을 적는다.
- 처리된 fps, 프레임 처리 시간 p50/p95, 추론 시간, CPU·메모리·가능한 GPU 수치를 별도 기록한다. 기존 UI의 순간 fps/ms만으로 p95를 계산했다고 쓰지 않는다.
- 현재 `processingMs`는 bitmap 취득 요청부터 결과 수신까지다. `inferenceMs`는 Worker 안의 추론 구간이다. 센서 노출→화면 표시 지연은 별도 측정이 필요하다.
- 30분/8시간 시험에서 5분 간격 자원 추이를 수집한다. 같은 연결/해제 사이클 후 Worker·트랙 수가 기준으로 돌아오는지, 메모리가 지속 증가하는지 조사한다. GC 순간 차이를 누수 확정으로 단정하지 않는다.
- `beauty.mjs`는 1080p 합성 영상·자연스럽게 설정의 10개 준비 응답 뒤 50개 응답에서 처리 fps와 Worker 왕복/추론 p50·p95를 기록한다. 왕복 시간은 Worker 전송부터 응답까지로 bitmap 취득·GPU 표시를 포함하지 않는다. 정식 장치 성능 측정이나 위 장시간 절차를 대체하지 않는다. 얼굴 좌표는 테스트 중 메모리에서 보호 픽셀을 찾는 데만 사용하며 보고서에 남기지 않는다.
- 현재 전용 장시간 성능 수집기는 없다. 추가 수집이 필요하면 현재 요청과 연결되는 최소 작업으로 정의한다. 관측에는 얼굴/랜드마크를 남기지 않는다.
- 평균 30 fps 등 이전 기획의 목표를 달성했다고 간주하지 않는다. 장치별 숫자 목표가 미확정이면 결과를 먼저 보고하고 합격선을 임의로 낮추지 않는다.

## 증거와 완료 판정

- 기록: 검증 시각/시간대, 작업 루트, 대상 버전/해시, 명령, 종료 코드, 관찰, 보고서 위치, 미검증 항목.
- `qa/e2e-report.json`, `qa/lifecycle-report.json`, `qa/beauty-report.json`, `qa/camera-permission-report.json`, `qa/preferences-report.json`, `qa/live-filter-report.json`, `qa/ui-layout-report.json`은 덮어써지는 로컬 결과다. 시작 시 running, 종료 시 passed/failed와 대상 경로·소스 해시를 기록한다. running/과거 시각/다른 대상은 통과가 아니다. 필요한 결과는 작업 기록에 보존하고 현재 프로세스 실패를 우선한다.
- `qa/`의 자동 화면은 합성 자산만 사용한다. 실물 환자 사진·프레임·랜드마크를 Git·문서·일반 로그에 넣지 않는다.
- 필수 시험 실패는 완료 불가다. 환경 부족은 “미실행 + 이유”로 적는다. 필요한 하드웨어가 없으면 자동 시험 통과와 하드웨어 확인 대기를 구분해 보고한다.
- 버그 수정 완료는 원래 재현의 해결, 관련 회귀 통과, 계약/문서 일치가 모두 필요하다. 기능 구현 완료·실물 검증 완료·상용 배포 가능은 별개 판정이다.
